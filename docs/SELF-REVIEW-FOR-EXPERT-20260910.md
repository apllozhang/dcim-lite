| 差分回放（厂商原版 vs 重建版） | 可比用例 **342**、**兼容率 87.1%** | ⚠️「可比用例中一致的比例」，**不是系统可用度**；342 之外尚有 9 条未产出 |

**差分回放的方法**：两侧各起全新干净沙箱（厂商镜像 / 重建镜像，各自独立卷），跑**同一套** golden 套件（315 个正式用例 + 并发/不变式场景），逐用例比对 HTTP 状态码与业务错误码。基线侧先复现了历史冻结证据（315 PASS / 0 FAIL），以证明套件与环境没有引入偏差。目标系统要求验证码时用环境变量门控的兼容层自动附加，**差异本身由 `DIFF-*` 探针用例显式记录**，不被兼容层掩盖。

## 4. 我做的主要技术判断及依据

| 判断 | 依据 | 证据强度 |
|---|---|---|
| 创建类接口应返回 201 | 厂商基线 45 次 201、重建 0 次；且它是 35 个夹具全部失败、227/350 用例跑不出来的根因 | 实测 |
| `rackId` 必须兼容 | 套件与 ALE 前端都用 `rackId`；只认 `targetRackId` 会使用户界面上的设备上架失败 | 实测 |
| 审批需单事务先占单后执行 | 并发 20 路批准原会重复执行；修复后实测恰一次生效、失败整体回滚 | 实测 |
| PDU 删除边界应画在「连接」而非「插座」 | 厂商码表存在 `PDU_SOCKET_CONNECTED`（连接层设防），且允许删除有插座的 PDU | 实测 + 推断（厂商是否级联清理插座无法判定） |
| 为"报废 PDU 但设备在用"设强制归档出口 | 业务确认该场景低频但真实存在 | 业务输入 + 设计判断 |
| 不复制厂商已知缺陷（如重复编码返回 500） | 评审指南与业务目标要求修复而非复刻 | 评审共识 |

**有意偏离厂商的行为**均登记在 `docs/COMPAT-DECISIONS.md`（S1-S11、D5），包括：写接口收紧为管理员、登录新增验证码、PDU 删除边界、强制归档新错误码。

## 5. 已知不足与盲区（请重点质疑）

1. **ALE 界面的端到端回归未收尾**。已实测：登录、页面渲染、行操作菜单、上架弹窗完整渲染（有截图）、字段与按钮齐全。**未完成**：在弹窗中通过级联选择器选定目标机柜并提交成功（当前卡在"点击后级联面板未展开"）。因此"ALE 界面点击上架后设备真的上架"这一条**没有端到端断言**。移位与审批流程同理未收尾（其中移位菜单项的真实名称也未确认）。
2. **差分兼容率的口径容易被误读**。87.1% 是"能对上的用例里对上的比例"，且分母只有 342/350。它不能推出"系统可用度 87%"。
3. **并发不变式断言仍有差异**（如上架并发的 `successes=1 vs 0`）。我判断是场景前置状态差异而非产品缺陷，但**没有逐条复核**，属未验证结论。
4. **单实例假设**：验证码、导入草稿、token 黑名单、登录限流均为进程内存实现。多实例部署前必须替换，当前部署形态下不阻塞。
5. **LDAP 仍是 TCP 连通性探测**，不验证 bind/证书/检索；接口语义已按厂商对齐（失败即 400），但"能连上"不等于"认证可用"。
6. **未做**：context 全链路传播、`/metrics` 与 tracing、服务层单元测试覆盖率数字、生产规模数据与性能压测、备份恢复演练。
7. **契约的请求体字段级 schema 未补全**：OpenAPI 覆盖了路径/权限/错误码/鉴权，请求体详情仍不完整。

## 6. 建议专家重点核查的方向

1. **差分用例集本身是否足以支撑兼容结论**：315 个用例的覆盖面、断言粒度（状态码+错误码 vs 字段级）、以及我方兼容层是否影响了对基线行为的刻画。
2. **"有意偏离厂商"的取舍是否成立**：尤其是 S1（普通用户写操作收紧为 403）与 D5（PDU 删除边界），这两条改变了对外行为，需要业务侧面确认。
3. **证据链可复现性**：冒烟、集成测试、差分回放是否能在独立环境复跑；门禁是否真的能拦住回归（本轮已发生过两次被门禁拦下的真实问题，见 §7）。
4. **事务与并发假设**：`SELECT ... FOR UPDATE` 的使用位置、乐观锁与条件更新的组合是否覆盖全部写路径；是否存在未纳入事务的跨表写入。
5. **数据不变量是否只在应用层保证**：U 位排他靠数据库 EXCLUDE 约束（可靠），但"PDU 与其插座/连接"的一致性主要靠服务层，缺数据库级约束。

## 7. 我自己的失误复盘（供参考判断工作可靠性）

1. **提交历史中混入 SSH 密码**。临时脚本被误提交，推送前扫描发现，用历史重写清除并核验远端零命中。教训已固化为"推送前扫凭据"。
2. **部署了缺一个已合并批次的旧二进制**。因本地 ref 未 fetch，构建产物回退了上一批修复；冒烟测试 `import-token-once` 立刻失败并被我捕获，修正后转绿。说明冒烟门禁有效，也说明"部署前确认基线"这一步不能省。
3. **ALE 自动化连续两次错误假设**（先假定弹窗是 `el-dialog`/`el-drawer`，后假定机柜选择器是 `el-select`），导致在同一个动作上多耗了数轮。根因是"用猜测代替观测"；后续改为先 dump DOM 再动手。
