## 3. 对字段差异分类文件的核对

### 3.1 做对了什么

- 已区分数据值差异、响应形状差异、厂商空壳修复和候选超集，避免盲目追求字节级复制。
- A、D 族正确识别了会直接影响 UI 的缺失：`currentPosition`、冲突设备、PDU sockets、连接关联对象、审批/下架回显、模板版本响应及排序。
- 保留候选系统中更准确或供新 UI 使用的字段是合理方向；自主产品不应为了“像旧系统”而恢复已知错误。

### 3.2 P0-C01：现在还不能称为“逐项分类闭环”

机器报告 `DIFF-REPLAY-FINAL-20260911.json` 记录的是 **51 个 FIELD_BREAK 用例**，而分类文档写“53 项差异”“约 12”“约 41”“约 30 处”，并以族级表格概括。一个用例中可能包含多个字段差异，因此“用例数、字段路径数、分类记录数”被混用了。

这会产生三个问题：

1. 无法证明每一个 FIELD_BREAK 都有且只有一个最终处置；
2. 新一次差分出现或消失时，无法自动判断分类是否过期；
3. `DATA_FIXTURE_NOISE` 目前依赖文字判断，没有同源数据快照或确定性 fixture 复跑作为证明。

**修复方法：**新增机器可读台账，例如 `tests/diff/field-diff-decisions.yaml`。每条至少包含：

```yaml
- caseId: S05-DEV-LIST
  field: data.items[*].currentPosition.startU
  classification: REQUIRED_BY_NEW_UI
  owner: backend-device-read-model
  decision: fill-current-position
  targetPhase: phase-1
  evidence: docs/DIFF-REPLAY-FINAL-20260911.json
  test: TestDevicePageIncludesCurrentPosition
  status: OPEN
```

随后给比较器增加门禁：所有 `FIELD_BREAK` 必须能映射到台账；禁止未知分类、重复记录和已关闭记录再次出现。文档由该台账生成汇总，不能再手工维护约数。

### 3.3 P0-C02：REAL_DEFECT 不能整体推迟给前端“复刻”

分类文件已经承认 A 族是 `REAL_DEFECT`，且说明旧 ALE 页面依赖这些数据。但处置又写“只读切片可以先按现有响应开发”。这在当前代码中已经形成真实冲突：`DeviceList.vue` 会读取 `row.currentPosition`，后端候选响应却缺少该对象，结果是已上架设备的位置列显示 `—`。

前端无法凭空恢复后端未返回的机柜、U 位、插座和关联设备数据。正确分工是：

- 后端提供稳定、自主、面向 ALE 新 UI 的规范读模型；
- 前端只做 DTO → ViewModel 映射，不猜测、不拼接缺失业务事实；
- 历史包装怪异可由适配层消化，但业务必需字段必须由服务端补齐。

因此 A 族至少应在对应只读页面进入 Phase 1 验收前关闭，而不是统一拖到写操作迁移前。

### 3.4 P1-C03：DATA_FIXTURE_NOISE 证据不足

`total`、`version`、`lifecycleStatus`、`heightU`、`startU/endU` 都可能承载业务语义。仅凭“库状态/顺序不同”不能自动认定为噪声。

应当为 B 族执行一次确定性验证：

1. 从同一 schema 和同一初始快照建立两个隔离数据库；
2. 固定时区、随机种子、用例顺序和分页排序；
3. 用同一 run-id 前缀分别运行厂商基线和候选；
4. 对 ID、时间戳等非确定字段做显式归一化；
5. 若值差异消失，才关闭为 `DATA_FIXTURE_NOISE`；若仍存在，重新分类为缺陷或主动差异。

在完成上述复跑前，B 族状态应为 `PROVISIONAL`，不能作为“无需修复”的最终结论。

## 4. 前端 Phase 0/1 代码发现

### P0-F01：资源树 props 绑定错误

`ResourceTree.vue` 使用了：

```vue
props="{ label: 'name', children: 'rooms' }"
```

这会把对象写成字符串属性。应改为动态绑定 `:props="treeProps"` 或 `:props="{ label: 'name', children: 'rooms' }"`，并用包含数据中心、机房、机柜三级数据的组件测试验证节点可展开。当前仅有验证码解析测试，未覆盖该页面。

### P0-F02：OpenAPI 生成类型没有进入实际调用链

仓库生成了 `src/api/generated/schema.d.ts`，但 `session.ts`、`resource.ts` 和 `resource/api.ts` 仍手写 `SessionUser`、`DataCenterNode`、`DeviceRow`、`DevicePage` 以及路径字符串。CI 只能证明“生成文件没有漂移”，不能证明页面真的遵守 OpenAPI。

应实现类型化请求入口：路径和 response body 直接派生自 `paths`/`components`，手写 ViewModel 必须通过显式 mapper 转换。禁止业务 feature 直接给 `getData<T>` 任意指定一个未经验证的 T。

### P0-F03：feature flag 和回滚声明尚未落地

ADR 声明使用 `window.__ALE_ROUTE_OVERRIDES__` 实现路由级回退，但源码没有对应读取、路由决策、默认值、审计日志或测试。当前“可 flag 回退”只是设计文本，不是可验证能力。

应提供：

- 类型化 runtime config；
- 按模块的新/旧路由映射；
- 配置加载失败时的安全默认值；
- 每个模块的回退 E2E；
- 部署清单中的 flag 注入和回滚操作手册。

### P1-F04：错误边界不是错误监控

`App.vue` 只执行 `console.error` 并在页面展示异常文本。生产环境无法聚合 requestId、版本、路由和用户角色，也没有告警。

建议先实现厂商无关的 `ErrorReporter` 接口，再选择 Sentry、OpenTelemetry 或自建采集端。至少记录：release SHA、route、API code/status/requestId、浏览器信息和匿名化角色；禁止采集 token、密码和验证码。

### P1-F05：会话与 HTTP 失败处理需收口

- 对运行期间 API 返回 401 没有全局清 token 和跳转登录逻辑；用户会停留在持续报错的页面。
- `getData`/`sendData` 直接把可选的 `data` 强制断言为 T，成功响应缺 data 时会把 `undefined` 伪装成合法对象。
- 验证码首次加载失败缺少页面级重试状态；`onMounted(refreshCaptcha)` 的拒绝没有在组件中处理。
- token 存储在 localStorage，仍需在安全模型中明确 XSS 风险、CSP 和未来改用 HttpOnly cookie 的决策。

### P1-F06：Phase 0 文档与实现不一致

ADR 的 Phase 0 描述包含“应用壳连 `/auth/me` 与 `/health/ready`”，当前只实现了 `/auth/me`；没有 `/health/ready` 调用或启动健康状态。应选择一种做法：补实现及测试，或者修正文档，不能保留无法复验的完成声明。

### P1-F07：前端测试门禁还不足以支撑双跑

当前 Vitest 仅验证验证码解析；Playwright 仅验证匿名跳转和验证码可见，且未进入 CI。至少补齐：

- API client：Envelope、401、403、409、网络超时、缺 data；
- session：刷新恢复、失效 token、登录失败、退出失败仍本地清理；
- ResourceTree：三级展开、空态、错误态；
- DeviceList：分页、搜索、位置、状态、空位置；
- Playwright：真实后端登录、只读资源树、设备列表、新旧结果规范化比较；
- 可访问性：键盘导航、表单 label、错误提示和基本 axe 扫描。

### P1-F08：跨平台工程复现性需要加固

建议：

1. 增加 `.gitattributes`，统一源码 `text=auto eol=lf`，Windows 脚本按需例外；
2. 根目录增加统一入口（Makefile、Taskfile 或 PowerShell 脚本），后端只测试 `./cmd/... ./internal/...`，避免 `node_modules` 中 Go 示例包污染 `go test ./...`；
3. 前端 CI 增加 Playwright job，并由 `webServer` 或容器编排显式启动依赖；
4. 将 GitHub Actions 固定到 commit SHA、PostgreSQL 固定镜像 digest、govulncheck 固定版本，减少供应链漂移。

## 6. Gate G1 重新定义

只有同时满足以下条件，才允许进入写操作预发布：

- PDU 聚合锁协议在真实 PostgreSQL race/integration CI 中持续通过；
- E2E 故意失败后的零残留证据可复跑；
- FIELD_BREAK 逐条台账和确定性 fixture 复跑完成；
- D01“活动供电连接下设备能否移位”获得业务书面裁定并进入后端不变式；
- feature flag、错误监控和一键回退均已实现并演练；
- 资源树与设备列表的真实后端新旧双跑通过；
- 新前端核心代码确实使用生成契约类型；
- Windows/Linux 干净环境门禁均可复现。

## 7. 最终方向判断

本轮没有出现需要停止自主前端重建的技术瓶颈。现在遇到的是**证据精度和工程闭环问题**，不是无法突破的反编译或架构瓶颈。

最合理的路线是：

> 后端读模型先补足业务事实 → OpenAPI 成为唯一契约 → 新前端按 ALE 设计体系重建 → 新旧只读双跑 → 低风险写操作 → 高风险状态机 → 旧 bundle 退出。

不要把目标误解为“让新前端适配所有旧后端怪异形状”。最终核心应是 ALE 自主领域模型、自主契约和自主 UI；旧系统只负责提供行为证据，不再决定新系统内部结构。
