## 4. 三处重点复核结论

### 4.1 P0-R01：D01 的 Connect × Move 仍有竞态窗口

当前 Move 路径：

1. `placeInTx` 通过 `GetDeviceLock(id)` 锁设备；
2. 在设备锁内执行 `CountActiveConnectionsByDevice(id)`；
3. 连接数为 0 时继续移动。

当前 Connect 路径：

1. 无锁读取 socket；
2. 锁 PDU；
3. 锁 socket；
4. 使用 `s.devs.GetDevice(in.DeviceID)` 无锁读取设备；
5. 无锁读取 active position；
6. 创建 connection。

Connect 既没有取得设备行锁，其设备读取也没有绑定当前 PDU transaction。以下交错仍可能发生：

```text
Connect                              Move
锁 PDU、锁 socket
读取设备旧位置（与 PDU 同柜）
                                     锁设备
                                     查询活动连接数 = 0
                                     移位并提交
创建 connection 并提交
结果：活动连接指向旧柜 PDU，但设备已经在新柜
```

正常路径测试 `TestMoveWithActiveConnectionBlocked` 只验证“已经连接后再移动”，没有并发启动 Connect 与 Move，也没有检查最终“连接 PDU.rack_id == 设备 active_position.rack_id”的数据库不变量。

#### 推荐修复

必须制定跨聚合统一锁序，建议：

```text
device → rack/PDU → socket → connection
```

Connect 可先做无锁定位，但进入决定阶段后应：

1. 在同一 transaction 内锁 device；
2. 锁 PDU；
3. 锁 socket；
4. 锁内重新读取 device active position、PDU 状态、socket 状态；
5. 再检查同柜、角色唯一性并创建连接；
6. 将所有 store 都切换为 `WithTx(tx)`，禁止 `s.devs` 基础连接逃出事务。

Move 已采用 device → rack，Connect 也必须从 device 开始，否则增加设备锁时会引入反向锁序死锁。

#### 必须新增的测试

- `TestDeviceMoveVsConnectRace`：至少 20–50 轮并发；最终只允许两个合法结果：Move 赢则 Connect 409，Connect 赢则 Move 409。
- 每轮直接查询最终不变量：不存在跨 rack 的 active connection。
- 在 Linux `-race` + 真 PostgreSQL 下执行。
- 增加带超时的死锁检测，并记录两路 HTTP 状态与最终数据库状态。

在该测试持续通过前，D01 不能标记为关闭。

### 4.2 C10 裁定：status 收权可接受，建议进一步改为投影语义

本次选择“缓存列 + Connect/Disconnect/ForceArchive 专属修改”是可接受的主动修复，比允许客户端直接写 status 安全。

但缓存列存在事实与投影漂移风险。建议：

- 数据库层增加约束或周期一致性检查：active connection 存在 ⇔ socket.status=CONNECTED；
- 写路径全部调用一个领域方法，不允许 repository 被其他 service 任意更新；
- 增加故障注入测试，证明 connection 插入失败、status 更新失败时整体回滚；
- 长期考虑把 status 改为查询投影或可重建缓存，不把它视为独立业务事实。

裁定：**C10 接受为 INTENTIONAL_FIX，不要求恢复厂商可直写行为。**

### 4.3 D01 同族裁定：Decommission 必须阻断带电设备

当前允许设备在活动连接存在时下架，会移除 active position，却保留 connection。此时系统无法再满足“设备与 PDU 同机柜”的领域不变量，也会产生业务意义上的悬空连接。

裁定如下：

- 普通 `decommission`：活动连接存在时返回 409 `DEVICE_POWERED`，提示先断开；
- 暂不自动断开，因为自动断电是具有较强业务影响的复合操作；
- 如未来需要强制下架，新增独立的 `decommission-impact` + `force-decommission` 两阶段接口，明确返回并确认将断开的连接数量，审计与业务变更同事务；
- 同时检查软删/报废设备、删除机柜、删除 PDU 等所有位置消失路径，确保不会留下 active connection。

## 5. 字段差异与 nightly 证据复核

### 5.1 C01 尚未形成逐项闭环

`DIFF-REPLAY-FINAL-20260911.json` 的 `v2_categories` 表示：

- `FIELD_BREAK = 51`，这是 51 个用例；
- 每个用例的 `diffs` 内可能有多个字段路径；
- 分类文档又使用“53 项”“约 12”“约 41”“约 30 处”等口径。

因此当前文档是“族级人工说明”，不是可以证明每一字段差异都已裁定的台账。需要建立 `field-diff-decisions.yaml/json`，以 `caseId + normalizedFieldPath` 为唯一键，记录分类、理由、owner、目标阶段、测试、状态和证据 SHA。

CI 应验证：

- 当前所有 FIELD_BREAK 均有台账记录；
- 台账中所有 OPEN 项仍能在报告中找到；
- CLOSED 项不得再次出现；
- 新增字段差异默认失败，不能自动落入“大类说明”。

### 5.2 nightly SUCCESS 的含义需要收窄

`diff-replay.yml` 当前仅在以下情况失败：

- `breaks` 非空；
- `compat_rate_status_code < 80%`。

它不会因为新的 `FIELD_BREAK`、字段兼容率下降但仍保持状态码兼容、或未分类形状差异而失败。工作流顶部“任何行为漂移都会失败”的注释因此过强。

nightly 首次定时 SUCCESS 证明了定时调度、候选构建、golden 执行和现有 status/code 门禁可以工作；它**不能证明字段契约无漂移**。

推荐增加：

- `unknown_field_breaks == 0`；
- `compat_rate_field` 不得低于已批准基线；
- 每类差异数量不得无解释增长；
- 机器台账完整性校验；
- 上传 candidate commit、镜像 digest、baseline digest 和台账 digest。

### 5.3 A/D 族优先级裁定

- A 族不是前端可以自行复刻的数据，应由后端提供规范读模型。
- A 族按页面作为 Phase 1 的前置依赖，不能等页面开发完成后再补。
- D 族中的排序、响应包装可以与对应页面并行；不必为了旧系统形状而污染新领域模型，可在 API adapter 层做兼容。
- 优先顺序：`currentPosition` → resource tree → U-layout → PDU/socket/connection 嵌套 → 冲突详情 → 写操作回显 → 模板响应和排序。

## 6. 前端 Phase 0 复核

### 6.1 P0-R02：资源树组件绑定错误

`ResourceTree.vue` 当前写法：

```vue
props="{ label: 'name', children: 'rooms' }"
```

这里传入的是字符串而不是对象。应使用 `:props="{ label: 'name', children: 'rooms' }"`，并补三级树组件测试。单纯构建成功无法发现这一运行时语义错误。

### 6.2 P0-R03：OpenAPI 生成类型没有真正约束业务调用

虽然 CI 会重新生成 `schema.d.ts` 并检查漂移，但业务层仍通过 `getData<T>(string)` 自行声明 T，路径也是自由字符串。`SessionUser`、`DataCenterNode`、`DeviceRow` 和 `DevicePage` 均为手写类型。

这意味着错误的路径或错误的响应结构仍可通过 TypeScript 编译。必须让 endpoint、参数、request body 和 response 从生成的 `paths`/`components` 派生，再通过显式 mapper 转为 ViewModel。

### 6.3 P0-R04：声明的 feature flag 尚不存在

ADR 声明 `window.__ALE_ROUTE_OVERRIDES__`，源码没有读取或执行它。当前也没有新旧路由映射、配置失败默认策略、回滚 E2E 或部署注入说明。“可单模块秒级回退”尚不可验证。

### 6.4 P1-R05：错误边界不等于错误监控

当前错误边界只在浏览器 `console.error` 输出。至少应建立可替换的 `ErrorReporter`，上报 release SHA、route、API code/status/requestId 和匿名化角色；禁止上传 token、密码、验证码和业务敏感内容。

### 6.5 P1-R06：HTTP 与会话错误处理尚未收口

- 运行期 401 没有全局清 token 和跳转登录；
- `Envelope.data` 是可选字段，却通过 `as T` 强制返回；
- captcha 首次加载异常没有明确错误/重试 UI；
- localStorage token 的 XSS 风险、CSP 和向 HttpOnly cookie 迁移策略尚未形成安全决策。

### 6.6 P1-R07：前端测试数量不足且 Playwright 未进入 CI

当前只有 2 个验证码解析单测；Playwright 只有匿名跳转冒烟，frontend job 未运行 `npm run e2e`，Playwright 配置也未负责启动 web server。不能据此认定登录、资源树和设备列表切片已交付。

### 6.7 P1-R08：跨平台工程体验未闭合

Windows 下 `npm run lint` 对 23 个文件失败。应增加 `.gitattributes` 固定 LF，并在 Windows/Linux 各执行一次干净 clone 门禁。

根目录存在 `frontend/app/node_modules` 时，`go test ./...` 还可能扫描依赖中的 Go 示例包。应提供统一脚本，显式测试 `./cmd/... ./internal/...`，或调整仓库布局/工作区规则，保证 README 中的标准命令不会因安装前端依赖而失效。

## 7. Phase 1 双跑验收口径裁定

不建议只给“信息架构”和“视觉连续性”设置一个可互相抵消的总分。关键业务错误不能被视觉高分抵消。

### 7.1 硬门槛，必须 100% 通过

- 数据字段和业务含义；
- 权限三态与菜单可见性；
- 401/403/409 等关键错误处理；
- 分页、筛选、排序和空态；
- session 恢复和失效；
- requestId 可追踪；
- 无旧 bundle 或运行时补丁依赖；
- 路由级回退可实际演示。

任何一项失败，模块不得切换。

### 7.2 质量评分，用于排序优化

在硬门槛通过后，再按以下权重评分：

| 维度 | 权重 | 建议通过线 |
|---|---:|---:|
| 信息架构与任务路径 | 45% | ≥ 90 |
| ALE 视觉连续性 | 30% | ≥ 85 |
| 可访问性与响应式体验 | 15% | ≥ 85 |
| 性能体验 | 10% | ≥ 85 |

综合分建议不得低于 88，且任何单项不得低于对应通过线。

### 7.3 双跑证据必须包含

- 同一 commit、同一后端镜像 digest、同一隔离数据快照；
- 新旧页面同一任务脚本；
- DOM/语义断言、API 规范化比较、截图三类证据；
- 浏览器版本、viewport、时间、run-id 和退出码；
- console error、失败网络请求和性能指标；
- feature flag 新→旧→新的回滚演练；
- 零残留检查。

## 10. 工程治理补充建议

### 10.1 供应链

当前仍使用 `actions/checkout@v4`、`actions/setup-go@v5`、`actions/setup-node@v4`、`anchore/sbom-action@v0`、`postgres:16-alpine` 和 `govulncheck@latest`。建议固定 action commit SHA、容器 digest 和 govulncheck 版本，由 Dependabot/Renovate 提交可审计升级 PR。

### 10.2 Metrics

203 的 `/metrics` 当前无需认证即可读取。内部隔离环境可以接受；生产应限制在管理网络、反向代理 allowlist 或独立监听地址，避免暴露容量、路由和时延信息。

### 10.3 文档证据纪律

- “已实现”“已部署”“已验证”“已关闭”必须分别使用，不可互换；
- 每项必须写明验证 commit，不以“main 最新”代替；
- CI 页面链接、run id、head SHA、结论和 artifact SHA 应同时登记；
- 运行时部署应提供镜像 digest 和 `/version` 响应，不能仅靠镜像 tag `0.2.0`；
- 自评材料发现错误后应更正原结论，而不只在后文追加说明。

## 11. 是否存在技术瓶颈

**目前没有不可突破的技术瓶颈。**

当前困难主要来自跨聚合并发设计、证据精确度、前端契约落实和新旧双跑工程量。这些都是明确可解决的工程问题，不需要继续追求“从 bundle 还原原始源码”。

今后的核心策略应保持为：

> 用旧系统证明外部行为，用自主后端定义可信领域事实，用 OpenAPI 固化契约，用 ALE 自主前端重建交互，再以新旧双跑控制切换风险。

完成上述 Gate G1 后，可进入低风险写操作迁移；在此之前，继续投入 Phase 0/1 是正确方向，但不得把“骨架存在”表述为“新前端替代已经完成”。
