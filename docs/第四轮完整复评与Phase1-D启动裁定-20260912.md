## 1. 一页结论

### 1.1 正式裁定

**裁定：Phase 1-D 可以立即启动；Gate G1 暂不通过；旧 ALE 编译产物暂不可退出。**

原因如下：

1. 后端高风险并发窗口已经从代码、锁序和集成测试三个层面得到实质修复，P0-A 可接受关闭。
2. 自主前端已经具备可构建骨架、统一 API 出口、登录与 401 收口、资源树和设备列表首批只读页面，足以进入 Phase 1-D 的新旧差分验证。
3. 19500 现场首页、`/legacy/` 和 `/health/ready` 均可访问，说明独立运行形态真实存在。
4. 但当前 CI 的“新→旧回退演练”没有真正加载旧前端，只验证了 URL 跳到 `/legacy/`；运行时环境变量也存在实际不生效的问题。
5. 字段台账实现了“未知字段路径默认失败”，但还不能识别“同一个已登记字段出现了新的错误值或新的差异类型”，因此不能称为完整的字段行为防漂移闭环。
6. 生产错误上报目前仅落到浏览器 `console.error`，独立部署配置也未纳入仓库，不能认定监控和部署体系已经源码化闭环。

### 1.2 当前完成度估算

以最终目标而不是以“反编译资料是否齐全”为分母，当前总体完成度建议评为 **约 70%～74%，中心值 72%**。

|---|---:|---|
| 证据、契约、数据模型与行为基线 | 88% | 已形成强基础，字段门禁仍需从路径级升级到语义级 |
| 自主后端 | 82% | 核心模型和高风险并发显著成熟，仍需持续补齐行为差分与运行验证 |
| 自主数据库与迁移体系 | 82% | schema、迁移和真实 PG 测试已具备；灾备、升级回滚仍需最终验收 |

这里最容易产生误判的是：**“前端工程骨架完成”不等于“自主前端完成”**。最终完成度的主要剩余工作已经从反编译研究转移到新源码实现、双跑验证和生产化交付。

预计还需要 **4～6 个有明确验收门的工程轮次**。如果每轮只是继续补文档而不交付页面、写链路和部署代码，轮次数没有意义；如果按本文批次推进，4～6 轮是合理区间。

### 2.2 P0-A：并发与带电下架

**结论：接受关闭。**

关键证据：

- `Connect` 已在同一事务中按 `device → PDU → socket` 加锁，并在锁内重新读取和校验设备、PDU、插座状态。
- `Move` 与 `Decommission` 先锁设备行，并在锁内统计活动连接；带电时返回 `409 DEVICE_POWERED`。
- 已补 `Move×Connect`、`Decommission×Connect`、`Decommission×Disconnect` 等多轮竞态测试，并检查“无跨机柜活动连接”“已下架设备无活动连接”等终态不变量。

这部分已经不是简单增加条件判断，而是把判断和写入纳入同一串行化边界，修复方向正确。后续只需保持统一锁序文档和测试，不应在业务页面开发中重新改变锁顺序。

### 2.3 P0-B：自主前端工程基础

**结论：主体完成，但只能评为“有条件完成”，不能按七项全部关闭。**

已经达标：

- Vue 3 + TypeScript + Vite 工程可以独立安装、测试、构建。
- OpenAPI 生成类型已经用于部分 GET/POST 响应类型和业务模型。
- 登录、验证码、会话、401 全局处理、错误边界具备测试。
- 资源树与设备列表已成为真实自主源码页面。
- Playwright 已进入 CI，并连接真实后端与 PostgreSQL。
- 19500 确有独立新前端部署，且现场 `/legacy/` 可以访问旧页面。

尚未闭环的事实：

1. `src/app/flags.ts` 读取的是 `import.meta.env.ALE_LEGACY_BASE`。Vite 默认只向客户端暴露 `VITE_` 前缀变量，因此该配置在没有额外 `envPrefix` 时不会按预期生效。
2. CI 将 `ALE_LEGACY_PROXY` 指向 `http://127.0.0.1:18080`，该地址是 Go 后端而不是旧前端。E2E 只等待 URL 以 `/legacy/` 开头，没有断言旧页面标题、标志性 DOM 或资源加载成功。因此该用例即使得到后端 404 页面也可能通过。
3. `sendData()` 对 `post/put/delete` 一律提取 `PostData<P>`，请求体仍是 `unknown`，调用方甚至使用 `as never`。这说明 OpenAPI 类型只“部分进入调用链”，尚未形成方法、路径、请求体、响应四者一致的强类型客户端。
4. `ErrorReporter` 目前默认只写 `console.error`，没有生产采集端、告警规则或可检索事件。接口基础完成不等于生产可观测性完成。
5. 仓库中未找到 19500 对应的 Nginx/Compose/Kubernetes/服务启动配置。当前是可访问的人工部署事实，但还不是可审计、可复建的“部署即代码”。

### 2.4 P1-C：字段决策台账与门禁

**结论：方法正确、进展显著，但门禁目前是“字段路径覆盖门禁”，尚不是完整的“字段语义门禁”。**

优点：

- 台账结构化、键唯一、分类和状态受枚举限制。
- 报告出现未知 `caseId + normalizedFieldPath` 会默认失败。
- OPEN 消失和 CLOSED 重现均有基础检查。
- 台账 SHA、commit、镜像摘要可以随 nightly 产物传递，具备证据链意识。

关键缺口：

1. 门禁只比较 `caseId + fieldPath`。若同一字段原来是可接受的动态 UUID，后来变成 `null`、错误枚举或敏感字段泄露，只要路径没变，仍可能被旧台账放行。
2. 80 条 `CLOSED` 全部带 `residualNoise=true`，即“仍可复现但被标为关闭”。这会削弱 CLOSED 的直观语义，也让新问题借同一路径进入豁免区。
3. `determinism_gate.py` 对全部 `DATA_FIXTURE_NOISE` 条目直接放行，同样没有验证实际值是否仍符合原来的噪声规则。
4. 兼容率下限是 68.0%，低于冻结报告的 70.3% 和本轮声称的 71.0%。仅靠该下限会允许明显倒退。
5. 台账有 207 条记录的 `backendTest`、207 条记录的 `frontendTest` 仍为空或 `-`。OPEN 条目允许没有现成测试可以理解，但 CLOSED 条目必须具备可运行的验证引用。

## 4. 四个开放项的裁定

### 4.1 `CLOSED + residualNoise` 是否接受

**不接受其作为最终状态，但接受作为本轮临时迁移状态。**

建议把一个含混状态拆为两个正交维度：

```yaml
implementationStatus: IMPLEMENTED   # 代码形状已经补齐
observationStatus: ACCEPTED_NOISE   # 报告仍出现，但符合已验证的噪声规则
noiseRule: UUID_V4 | TIMESTAMP_TOLERANCE | ORDER_INSENSITIVE | FIXTURE_PREFIX
```

只有当前报告中不再出现、或经过规范化后完全相等的条目，才允许 `observationStatus: CLOSED`。这样既能表达“功能已实现”，又不会谎称“差异已消失”。

### 4.2 一次双库成功是否足以把 B 族永久翻转

**一次只够形成“暂定接受”，不够形成永久结论。**

最低验收建议：

- 同一候选镜像连续 3 次 scheduled nightly 成功；
- 每次均使用两套全新数据库卷；
- 改变 run 前缀、并发 seed 或用例顺序，避免偶然一致；
- `breaks=0`、`missing=0`；所有噪声都满足明确 `noiseRule`；
- 三次产物保留 commit、镜像 digest、数据库镜像 digest、台账 SHA。

这不阻塞 Phase 1-D 开发，但在达到条件前应标 `PROVISIONAL_ACCEPTED`，不应永久关闭。

### 4.3 P1-D 与供应链固定的顺序

**先用一个小批次修复前端回退证据，再启动 P1-D；供应链固定与 P1-D 并行，且必须在 G1 验收前完成。**

如果团队只能串行：先做回退修复和供应链固定，这两项范围小、风险低；随后集中进行 P1-D。不要让供应链工作阻塞开发启动，但也不要把它无限后置。

### 4.4 A 族后续优先级

应按页面依赖排序，而不是机械按字段数量排序：

1. P1-D 当前切片：资源树、设备列表及 `currentPosition` 的新旧双跑和视觉/交互差分。
2. PDU 只读切片：`sockets → connections`，为后续供电页面建立稳定读模型。
3. 设备上架/移位写切片：`conflictDevices → 写后回显 → 错误码/确认框`。
4. 通用列表语义：分页、空值、排序、筛选、包装结构。

`conflictDevices` 对写链路很重要，但不应阻塞当前只读 Phase 1-D 的完成。

## 5. 下一轮派工清单

### P0-R1：修复真实回退闭环

目标：CI 必须证明旧页面真的加载，而不是仅证明地址发生变化。

实施：

1. CI 启动一个独立 legacy 静态站点容器或 Nginx 服务，禁止把 legacy proxy 指向 Go API。
2. `/legacy` 代理需要明确 `rewrite`/路径策略，并验证 hash 路由、JS/CSS 资源均为 200。
3. E2E 在跳转后断言旧页面独有的标题或稳定 `data-test`；同时监听 `pageerror`、失败请求和 4xx/5xx 主文档。
4. 再从旧页面切回新页面，断言新资源树真实渲染和 API 请求成功。
5. 增加生产 19500 的只读冒烟脚本，并纳入部署后验证。

验收：错误地把 legacy 指到后端时测试必须失败；正确旧站点时 `new → legacy → new` 全链路通过。

### P0-R2：修正 feature flag 配置和治理

实施：

- 将客户端构建变量改为 `VITE_ALE_LEGACY_BASE`，或在 Vite 中显式配置受控 `envPrefix`。
- 增加测试，构建时注入非默认地址并验证最终 bundle 使用该值。
- 明确生产优先级。建议部署端强制策略高于 localStorage；URL/localStorage override 只在非生产或授权管理员调试模式开放。
- feature flag 不是权限控制，后端仍必须独立做鉴权。

验收：默认、部署注入、管理员临时覆盖三种情形均有自动化测试；普通用户不能永久绕过灰度策略。

### P0-R3：把 19500 部署纳入源码

至少提交：

- 新前端多阶段 Dockerfile；
- Nginx 配置，明确 `/api`、`/health`、`/legacy`、SPA fallback、静态资源缓存和安全头；
- Compose 或等价编排文件；
- 环境变量示例与密钥注入说明；
- 健康检查、升级、回滚、备份恢复和部署后冒烟脚本；
- 镜像 digest 与版本标签生成规则。

验收：在一台干净主机上，只用仓库文件和明确的密钥输入即可重建 19500 等价栈；不依赖操作者记忆或服务器上未归档配置。

### P1-R4：升级 OpenAPI 强类型客户端

目标：方法、路径、请求体、query/path 参数、成功响应和错误响应均由 OpenAPI 推导。

优先方案：采用 `openapi-fetch` 或等价成熟客户端；备选方案是自行实现 `PathsWithMethod`、`RequestBody`、`ResponseData` 泛型。禁止继续使用 `body?: unknown` 和业务侧 `as never` 绕过类型系统。

验收负例：

- GET 路径用于 POST 时编译失败；
- 缺少必填 body 字段时编译失败；
- PUT/DELETE 返回类型与契约一致；
- OpenAPI 变化后生成文件 drift gate 和业务编译至少有一个失败。

### P1-R5：字段门禁从路径级升级到语义级

为每个豁免条目增加可执行规则，例如：

```yaml
comparison:
  rule: UUID_V4
  leftMustMatch: true
  rightMustMatch: true
```

可支持的最小规则集：`EXACT`、`ABSENT_OR_NULL`、`UUID_V4`、`TIMESTAMP_TOLERANCE`、`ORDER_INSENSITIVE_BY_KEY`、`FIXTURE_PREFIX`、`SYMMETRIC_SWAP`。门禁必须读取左右实际值并执行规则，不能只核对路径是否登记。

同时执行：

- 基线从固定 68.0 改为 ratchet：不得低于最近一次已批准主干基线；确需下降必须提交带理由的基线变更。
- 为不同类别设置预算，`REAL_DEFECT` 不允许增长。
- CLOSED 条目必须存在且能定位到可运行测试；OPEN 可允许测试为 `-`，但必须有 owner 和 targetPhase。
- 增加负向测试：在同一路径注入错误枚举、`null`、敏感值和超差时间戳，门禁必须失败。

### P1-R6：接入真实前端可观测性

实施：

- 提供生产 `ErrorReporter` adapter，可落内部日志 API、Sentry 或既有监控平台；
- 上报 release、route、error fingerprint、API code、requestId 和匿名角色；
- 对 token、密码、验证码、个人标识执行字段白名单；
- 定义错误率、白屏率、401 激增、接口 5xx 的告警阈值；
- E2E 注入一个受控异常，验证事件可在接收端检索，而非只在控制台出现。

### P1-D：资源树和设备列表新旧双跑

前置条件仅为 P0-R1、P0-R2 完成，不需要等待所有后续模块。

每个页面至少覆盖：

- 正常数据、空数据、加载、失败、重试、401、403；
- 分页、搜索、筛选、排序及刷新后的状态保持；
- 字段显示、空值文案、时间/容量格式、状态颜色；
- 键盘操作、焦点、窄屏和常见分辨率；
- API 请求集合、响应字段、页面截图和关键 DOM 快照的新旧差分；
- 新页面失败时的模块级回退与审计记录。

退出标准：核心场景全部通过；新增未知差异为 0；已接受差异均有机器规则；连续三个候选版本没有严重回归；feature flag 可在不重新部署后端的情况下安全切换。

### P1-R7：供应链固定

需要固定：

- GitHub Actions 使用完整 commit SHA，并用注释保留版本名；
- `postgres:16-alpine` 改为 digest；
- `govulncheck@latest` 改为明确版本；
- SBOM 工具、Node、Go、Playwright 浏览器版本保持可追溯；
- 增加依赖更新机器人或月度升级任务，避免“固定后永久不更新”。

验收：同一提交重跑时工具和基础镜像来源一致；升级必须经过独立 PR、测试和 SBOM 差异审查。

## 6. 建议的后续 4～6 轮路线

如果第 4～8 轮范围控制良好，第 9 轮可以只是发布验收而不是继续开发。

## 7. 旧 ALE 编译产物的退出条件

只有同时满足以下条件，才可以从运行链路移除旧产物：

1. 所有生产使用模块均由 `frontend/app` 自主源码实现，不存在长期 iframe、静态资源复用或隐式跳转。
2. 新旧差分中的未知行为差异为 0；接受差异均有书面理由和机器规则。
3. 所有高风险写链路经过真实 PostgreSQL、并发、权限、审计和失败恢复验证。
4. 部署、配置、迁移、监控、备份、恢复和回滚全部在仓库中可重建。
5. 至少完成一次从备份恢复到新环境的演练和一次生产等价蓝绿/回滚演练。
6. 旧页面连续一个稳定观察期无实际回退使用；建议不少于两个发布周期。
7. 法务/商务结论和资产清单归档完成，但按既定裁定不作为工程开发阻塞项。

## 8. 给执行人员的明确指令

下一轮不要继续扩大文档数量，先交付 P0-R1～P0-R3 的可运行改动，再进入 P1-D。提交时必须提供：修改文件、测试名、原始测试输出、commit、CI 链接、现场验证和失败负例。尤其要证明“错误配置时门禁会失败”，因为只有成功截图不能证明门禁有效。

本轮没有出现无法继续的技术瓶颈。现有问题都属于可工程化解决的测试真实性、类型约束、部署可复现、噪声建模和生产可观测性问题。真正的约束是工作量和验收纪律，不是反编译技术本身。

## 9. 最终意见

项目已经越过“能否重建”的可行性阶段，进入“如何有纪律地完成自主替代”的实施阶段。后端可信度和证据工程显著提升，自主前端也具备正式开发条件。现在应当启动 Phase 1-D，而不是继续等待所谓 100% 反编译还原；同时必须保留旧 ALE 作为对照和回退，直到自主前端、部署与可观测性达到本文退出条件。

**本轮结论：Phase 1-D 有条件 GO；Gate G1 NO-GO；全量自主替代尚未完成。**
